# i18n S7 — localized emails (whole-template-per-locale)

**Status:** SUPERSEDED 2026-07-28 — delivered by
`.claude/tasks/20260728-auth-email-templates-in-code.md`, with a DIFFERENT design
**Plan:** `.claude/tasks/i18n/20260720-i18n-l10n-foundation.md` → S7
**Security-critical:** no (but see the superseding task — HTML escaping stopped being a criterion
because it stopped being a risk)

> ## ⚠ The design below was built, gated, and then replaced. Read this first.
>
> The Markdown-template design in this document was implemented on 2026-07-28 as a vertical slice
> (the account-activation email) and put through `/feature-review`. **The gate is what killed it.**
>
> The user's objection was that a placeholder-substitution engine eventually mails a literal
> `Hello ###FIRSTNAME###!` to a real person. That is not hypothetical: Reviewer 1 found `senderName`
> was substituted into the body with **no assertion anywhere**, so deleting it from the args map
> shipped `{{senderName}}` to every recipient with the whole suite green. Leaving unknown
> placeholders untouched was a deliberate decision in this design, which means the failure mode was
> by design.
>
> Three HIGH and three MEDIUM confirmed findings were eliminated by removing the mechanism rather
> than patching it (double-escaping of template-authored attributes, a scheme allowlist that broke
> `myapp://` deep links, a parse error 500-ing sign-up after the account was written, an escaper with
> unreachable attribute contexts, the activation token being reachable from the never-anonymized
> subject, and a path-traversal guard needed on a user-controlled locale).
>
> **What survived from this document, and is now implemented:**
> - whole-email-per-locale — never assemble a mail from per-key fragments
> - the locale chain `de-CH → de → en`, and `LanguageSettings.messaging` finally having a consumer
> - app override of framework mails, and the framework shipping minimal defaults
> - the layout / content split, with the layout carrying the locale
>
> **What is void:**
> - Markdown templates, front-matter subjects, `{{placeholder}}` substitution (§1–3, §5–7)
> - the commonmark dependency (§10)
> - APP-OUTER vs locale-outer precedence (§8) — an app now replaces a whole template, so there is no
>   precedence puzzle and no partial-override warning to emit
> - the codegen/checker "emails mode" (§4) — there is nothing to check that the compiler does not
>
> Everything below this box is kept for the reasoning, not as instructions.


## Design (agreed 2026-07-22)

Current state: the auth emails are built inline in
`funktor/auth/src/jvmMain/kotlin/AuthRealm.kt` (`DefaultMessaging`) with kotlinx.html — layout and
content interleaved, English hardcoded.

**UPDATED 2026-07-27: there are now THREE emails, not two.** Account activation
(`.claude/tasks/20260727-account-activation.md`) added `sendAccountActivationEmail`, and the resend
feature made it a mail users receive more than once. It is the newest and smallest template, so it is
the cheapest one to convert first.

Also still true and still worth stating: **`LanguageSettings` has zero consumers.** It landed with the
`AuthUser` bound as this stage's prerequisite and nothing reads `user.language` anywhere in the repo
(verified 2026-07-27). S7 is what makes it real; until then, every realm mails English regardless of
what a user has stored.

**Core principle: the translation unit is the WHOLE email, per locale.** Never assemble sentences
from catalog keys — fragment-assembly does not survive across languages. Locale resolution picks one
whole template via the existing fallback chain (`de-CH → de → en`); languages are never mixed within
one email.

1. **Layout / content split.**
   - *Layout* stays Kotlin (kotlinx.html): branding chrome, header/footer, the `body {}` skeleton —
     language-independent, one content slot. Today's `DefaultMessaging` markup becomes the layout.
   - *Content* is one **Markdown document per email per locale**:
     `src/jvmMain/i18n/emails/password-changed.en.md`, `.de.md`, `account-recovery.en.md`, ...
2. **Markdown with raw-HTML passthrough.** Email clients need special HTML (inline styles only for
   font sizes/colors), so templates will accumulate embedded HTML over time — that is expected and
   fine for v1. *Related future work (not recorded yet): a reusable content editor working across
   email/web/apps would eventually supersede hand-edited templates.*
3. **Subject via front-matter** in the same file, so subject + body translate together:
   ```markdown
   ---
   subject: "{{applicationName}}: Recover your Account"
   ---
   # Heads up!
   Click the link below ...
   [Recover account]({{resetUrl}})
   ```
4. **Reuse the S1–S3 machinery.**
   - Codegen: `I18nPlugin` grows an emails mode. The fallback (`en`) template defines the placeholder
     API surface (D8) → generated typed accessor with forced named params:
     `emails.accountRecovery(locale, applicationName = ..., resetUrl = ..., senderName = ...)` →
     `EmailContent(subject, html, text)`.
   - Checker: S2 rules lifted to templates — `requiredLangs` must have every email template; locale
     variants may omit placeholders, never add unknown ones. Front-matter subject placeholders are
     checked too.
   - Substitution: the S1 single-pass resolver.
5. **HTML-escape substituted values (hard requirement).** A user display name substituted into HTML
   must not become an injection vector; URL placeholders in attribute context need attribute-safe
   escaping. Adversarial tests required (script tags, quote-breaking, javascript: URLs in
   `{{resetUrl}}`-style slots).
6. **Format-before-substitute.** Accessors take typed values (`MpZonedDateTime`, numbers); values are
   formatted with the RECIPIENT's locale via `i18n.format` before substitution (D9 seam — default
   impl for now, improves when D9 lands). Templates never contain formatting logic.
7. **Plain-text alternative** generated from the same Markdown (multipart) for deliverability.
8. **App override of framework templates (added 2026-07-22).** The framework ships MINIMAL default
   templates for the auth-flow emails; apps must be able to override them. Two levels:
   - *Wholesale* (exists today): apps provide their own `Messaging<USER>` implementation instead of
     `DefaultMessaging` (`AuthRealm.messaging`, `AuthRealm.kt:165`) — unchanged.
   - *Per-template* (new, i18n-aware): apps drop their own `account-recovery.de.md` etc. and the
     resolver prefers app templates over framework templates — the template analog of D3 ("override
     is runtime resolver data").
   - **DECIDED (user, 2026-07-22): APP-OUTER precedence + checker warning.** Unlike the message
     resolver (locale-outer), email templates resolve app-first across the WHOLE locale chain, then
     framework: an app's `en` template beats the framework's `de` one, because app templates carry
     branding/legal content that must always ship. To keep the wrong-language case rare, the i18n
     CHECKER warns on partially-overridden emails: overriding an email in one locale but not all
     `requiredLangs` produces a build warning pushing apps to complete their overrides. (This is a
     deliberate, documented divergence from the message-catalog resolution semantics — emails only.)
9. **User language settings on the USER object (added 2026-07-22).** MOVED to the prerequisite
   task `20260722-auth-user-seams-refactor.md`: `LanguageSettings` (extensible value object) lands as
   part of the `AuthUser` bound (`AuthRealm<USER : AuthUser>`) together with `AuthUserAdapter`. S7
   consumes `user.value.language.messaging` directly.
   - Email locale resolution order: `user.language.messaging` → realm default language → `en`.
   - **Locale hygiene (domain-review note):** `language.messaging` is a free-form BCP-47-ish string
     tag. S7 MUST run it through `Locale.parse(...)` (normalizes case/separators) at the resolution
     boundary so a stored `"DE"`/`"de_CH"` cannot mis-resolve the fallback chain; the future
     profile-UI writer should persist `Locale.parse(x).tag` (normalized).
   - A profile-settings UI to edit it is a separate later task.
10. **Markdown renderer dep (JVM):** commonmark or flexmark — **check the newest version online at
    implementation time** (never from memory), per the standing dependency rule.
11. **Anonymization must survive templating (added 2026-07-27).** Every auth mail is persisted through
    `EmailStoring.withAnonymizedContent`, which strips links from the STORED copy so live tokens do not
    land in the sent-messages inspector. Templates carry `{{resetUrl}}` / `{{activationUrl}}` slots, so
    the anonymizer must keep seeing a real href in the rendered output — a template that emits a link
    in a shape the regex does not match would silently start persisting live tokens. The e2e specs
    already assert this positively (`storedBody shouldContain "#anonymized"`); keep those assertions
    pointed at the rendered template.

## Spec / acceptance

- [ ] Emails mode in codegen + checker (en defines API; parity for `requiredLangs`; front-matter subject)
- [ ] `password-changed` + `account-recovery` + `account-activation` templates in `en` + `de`
- [ ] Layout extracted; `DefaultMessaging` renders template content into the layout slot
- [ ] Substituted values HTML/attribute-escaped + adversarial tests
- [ ] Typed accessor values formatted via recipient locale (D9 default impl)
- [ ] Multipart: text part generated from Markdown
- [ ] `LanguageSettings` value object (commonMain, serializable) + ONE access seam on the realm/user;
      demo user models carry it; resolution `user.language.messaging` → realm default → `en`
- [ ] Per-template app override: APP-OUTER precedence (app templates win across the whole locale
      chain, then framework); checker warns when an app overrides an email in some but not all
      `requiredLangs`
- [ ] Recipient locale threaded through `Messaging`
- [ ] Backend e2e (`AppSpec`/`AppUnderTest`): all three emails render in `en` AND `de`; fallback chain
      picks whole template; no mixed-language emails; app-override template wins over framework default
- [ ] The existing mail e2e specs (`PasswordResetEmailE2eSpec`, `AccountActivationEmailE2eSpec`) assert
      SUBJECT STRINGS (e.g. `"Funktor All Test: Activate your Account"`) and extract the link with
      `hrefs().single()`. Both assumptions move into the templates — update those specs deliberately
      rather than loosening them until they pass, and keep `single()`: an auth mail carrying exactly
      one link is a property, not an accident.
