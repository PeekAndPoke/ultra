## Decision list

1. **Shipped but never gated (00158 log API, 00147 arrays): run a gate now, or close as DONE on production evidence?**
   Options: (a) a standard `/feature-review` round on each; (b) close as DONE, with a note that they have run in
   production since v0.109.0. Recommendation: (a) for 00158, because it changed public API and the lifecycle requires
   the gate; for 00147, put the F1/C8/F6 fix in first and gate it together with them.
2. **Slumber lookup and cache strategy (A1/A3/A5, D3/D4): how to make `SlumberConfig.Lookup` thread-safe and stop
   configs that share it from polluting each other?** Options: (a) `ConcurrentHashMap` with a NULL sentinel, a fresh
   `Lookup` on every derivation that changes attributes, and `lookup` moved out of the data-class constructor (API);
   (b) keep the shared lookup and key it by (attributes, type). Recommendation: (a). Then key `SlumberCache` by
   (config identity, data identity) and hand out read-only maps (D3/D4). This is the only live concurrency hazard
   left on the production request path. Size M.
3. **`SlumberException : Throwable` to `RuntimeException`, with a `cause` (B1/B8)?** Options: change it (callers'
   `catch (e: Exception)` start catching it, as in `BackgroundJobQueued.kt:36`, which wants that), or keep it.
   Recommendation: change it, and raise `SlumberException` instead of `error()` in A6. B4 and A6 follow from this.
4. **Slumber fixes that change behaviour or the wire (D1, C1, E8, B5/F4): fix them, or document them?**
   Recommendation: D1, the default wins for an absent key (kotlinx semantics; only absent keys change). C1, put
   polymorphic-child above value-class (no such type found in the repo; UNVERIFIED). E8, PARK. B5, rethrow the
   first-pass error when the second pass succeeds. One commit per item, each mutation-checked, because Slumber is
   battle-tested and every server runs it.
5. **Log forging (L1/L15): escape CR/LF in `LogAppender.format`, or leave it to the red team (ULTRA-00150)?**
   Recommendation: escape `\r`/`\n` in the message, and prefix the stack-trace continuation lines in the console
   format (S). SLF4J backends get the Throwable separately since 00158.
6. **L11: create a kontainer ticket for a `dynamicPrototype` injection type?** Recommendation: yes, a new ticket
   outside this epic (kontainer is battle-tested; L). Close L11/L12 here with a pointer to it.
7. **How strict should primitive and time coercion be (G1-G4, H2, H7)?** Recommendation: NaN, overflow and
   out-of-range values awake to null, as the Long codec already does. H2: keep both wire units (changing them makes
   stored data unreadable) and add range validation that returns null. H7: keep accepting any `MpTimezone` string,
   as ULTRA-00294 did, so old records stay readable.
8. **00211: how should `MpZonedDateTime` be represented?** Options: (a) store the instant (or the offset) and
   derive the local fields, like java's `ZonedDateTime`; (b) keep local + zone and add an offset field.
   Recommendation: (a), decoding from the `ts` that `MpDateTimeRawData` already stores, so the wire format does not
   change. Ship it in the same breaking release as 00210. Size L, persistence, mutation-checked.
9. **00210: what are the new type names, and do inputs switch too?** Recommendation: `MpMonth` and `MpDayOfWeek`;
   inputs keep accepting kotlinx types (the maintainer's rule); remove `offsetAt` in favour of `offsetSecondsAt`. Two
   call sites outside the module.
10. **00234: should `subList` be a live write-through view or a read-only snapshot?** Recommendation: a live view,
   since that is the contract and writes go through the parent's notifying `set`/`add`/`removeAt`. First probe whether
   `chunked()` reaches `subList` at all, and correct `mutator/core/CLAUDE.md` if it does not.
