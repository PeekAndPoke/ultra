## Decisions

1. **Error disclosure design (00055/00053): record A/B/C and whether to build `HasClientMessage` + error id at all.** After 00292 production no longer renders internal messages, so the original driver (AQL in prod) is closed. What is left: non-prod/staging bodies carry stack traces by environment, 400 messages are written by hand, and no correlation id exists. Options: (a) build the full design (C: identity-gated, `HasClientMessage`, error id, staged rollout; L); (b) small slice: `errorDetail` gates on superuser instead of environment, keep messages as is (M); (c) stop at 00052 (unknown env = production, so staging gets no traces) and close 00053/00055 as superseded by 00292 plus 00052 (S). **Recommend (c) now, (b) as the only follow-up; the full design only when a downstream app needs per-exception client messages.** Auth gets its own `AuthError.clientMessage` (D3) without the global interface; the interface can come later.
2. **Unknown environment (00052): Option A (one line: derive `isProduction`/`isNotProduction` from `isDevelopment`) now, sealed type that fails boot later or never?** Recommend A only, and ship it with the inverted tests (`KtorConfigSpec.kt:30-44`, `ApiStatusPagesSpec.kt`). It is a breaking change for staging: add a CHANGELOG line. Boot failure on unknown env: PARK (ops sign-off).
3. **Sign-up "User already exists" oracle (00051): B (equalise failure only) or A (neutral 200 for every sign-up, mail the owner of an existing address)?** Activation now exists, so A is feasible, but it changes the client flow (breaking, kraft/auth frontend). Recommend A, as its own ticket after the Code/clientMessage change (which can ship first and also removes the echo of the message text).
4. **Timing oracles (00051): sign-in dummy hash now; sign-up and recovery?** Recommend sign-in dummy verification now (S-M, unknown-user path), assert hasher call counts not wall-clock; sign-up and recovery timing PARK to a ticket (needs mail queue; recovery response is already uniform).
5. **`estimateAccess` of an empty rule list (00059): keep Granted or become Denied/Unknown?** With the floor only hand-built routes hit it. Recommend DROP: keep, add a KDoc line, close 00059.
6. **Route-ownership hardening (00094 items 1, 2, 6a; 00097 item 1): schedule or park?** All are new boot checks that can break downstream apps at start and are not live holes (floor covers auth; org isolation is built). Recommend: do `validateUriPattern` -> `RouteBootCheck` (00094 item 1) only inside the ULTRA-00098 module-builder redesign; park the rest, unchanged, as a "route ownership" epic of its own with the red-team tickets; take 00094/00097 out of this epic.
