## Decisions for the maintainer

1. **D1 (00060, go/no-go; nothing blocks it).** Build the depth guard as designed in the ticket (skip-and-log, default 5, `VaultConfig` knob, depth carried on the `launch`)? Recommendation: yes, vault-only, and no production hook exists today so nothing can regress (ticket's own point). Alternative: Document-only (ticket rejects).
2. **D2 (delete path, API break).** Should Karango `remove(idOrKey)` throw on everything but Arango error 1202 (00313), and should after-delete hooks fire only when `RemoveResult.count > 0` and also on the bulk `remove(Iterable)` (C8, C9)? Recommendation: yes to all three as ONE ticket and one CHANGELOG "breaking" line; first grep the callers of `remove(` on Karango repos. **D2b (00111):** make Monko `findById` return null for a foreign collection prefix (option 1) and also type `AuthUserAdapter.loadById` (option 2)? Recommendation: option 1 only, with a `MatrixTest2d` differential test; option 2 is a funktor/auth change, leave it to the auth epic. Do D2b together with the `ensureKey` users in `remove`/`insert`.
3. **D3 (00300, security).** The ticket is a review, not a fix; pick the fix shape: rewrap at the repository boundary, redacting log formatter, or keep logs out of insights. Recommendation: rewrap at the driver boundary (`KarangoDriver.kt:142` drops `e.message` from the message, keeps it as `cause`; new `MonkoQueryException` for `MongoException`, message = operation + collection + var names, as Karango already does), plus keep the cause out of `ApiStatusPages` detail. Do it after D2 (same code area). Re-parent the ticket under 00254 or keep it under 00253, one epic only.
4. **D4 (00141/00142 sequencing and Karango approach).** Monko is ready now. For Karango: first fix `matches()` and `createHelper` to compare full index shape (own S/M ticket; it forces a rebuild of every existing Karango index on deploy, so decide staged rollout), then pick: sparse unique index on a discriminator field maintained by an `OnBeforeSave` hook, or ArangoDB `computedValues`, or enforce in app code under the per-org lock. Recommendation: Monko first, then analyzer fix, then discriminator via hook; check the Arango server version in use before designing (UNVERIFIED here).
5. **D5 (S1/Q2 soft-delete enforcement).** Enforce at repository level or keep opt-in plus docs? Recommendation: PARK with a docs note ("what will bite me" in vault skill); the maintainer already decided against filtering `findById`, and enforcement is a large API change.
6. **D6 (00120 sweep).** Delete the two dead public helpers (`resolveAll`, `filterValueIsInstanceOf`) or keep? Recommendation: keep, add two 5-line tests, close the sweep ticket as DONE-with-note (the scan fixes and 25 specs already cover the blast-radius list; coverage tooling is not worth adding). Deleting is a public-API break for zero gain.
7. **D7 (00101, 00103).** Keep both as `future` ideas, remove them from the epic's critical path. 00101 needs ULTRA-00102 and the GDPR design; 00103 is small but has no incident behind it. Recommendation: PARK both, move out of the epic so it can close.
8. **D8 (closing ULTRA-00140).** It is a backlog; close it by moving the READY findings above into ONE new ticket "Vault scan leftovers" (C3, C4, C10, C12, A6, B4, D-list small items) and marking the rest DONE/DROP/PARK as in the tables. Recommendation: yes; a PAUSED mega-ticket keeps the epic open forever.
